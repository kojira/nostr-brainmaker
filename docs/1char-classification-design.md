# 1文字分類（脳内メーカー風）設計メモ

> 本ドキュメントは**設計のみ**。コードは含まない。Nostr の1投稿を入力とし、オリジナルの脳内メーカーのように「1文字」を出力する分類器を、データ収集→教師ラベル付与→学習→ブラウザ推論まで一気通貫で設計する。

---

## 1. ゴールと非ゴール

### ゴール
- **入力**: Nostr の1投稿（`content` テキスト1件）。
- **出力**: 脳内メーカー風の漢字／記号 **1文字**（例: 愛, 欲, H ...）。
- **本番の固定クラス集合は観測 46 ラベル**への単一ラベル分類とする。パイロットのラベリング工程では、これに QA 専用の `分類不能` を 1 つ足した **47 ラベル**を一時的に許容する（§2）。
- 最終的に**ブラウザ完結（静的・オフライン）**で推論できること。現行アプリが採用しているヒューリスティックなトークナイズを、学習済み小型モデルに置き換える。
- 最終ブラウザモデルは**常に観測 46 ラベルのいずれか1つを必ず出力する**（棄却・`分類不能`・UNK を返さない）。

### 非ゴール
- 複数文字・文章生成（例: 「愛と欲」など複合表示）は対象外（将来拡張）。
- 脳内メーカー本家の内部ロジック再現や著作物の複製は目的としない。あくまで「1文字に要約する」体験の独自実装。
- サーバ常時推論・課金APIへの実行時依存は非ゴール（学習時のみ外部APIを使う）。
- ユーザ識別・プロファイリング目的の利用は非ゴール。

## 2. ラベル集合計画（パイロット在庫）

### 方針
- 脳内メーカー風の**1文字キャラクター在庫**を採用する。
- 在庫は**オリジナル（脳内メーカー本家）で実際に観測された 46 文字**を基準に確定する。以前の暫定 v0（42ラベル）も、直前に縮小した 15 ラベル案も、いずれも観測リストと一致していなかったため破棄し、**観測 46 文字**を本番在庫の基準とする。
- パイロットのラベリング工程に限り、ここに QA 専用ラベル `分類不能` を 1 つ足した **47 ラベル**を許容する。
- 凍結後はバージョン管理し、勝手に増減させない。

### 観測ラベル在庫（Observed Set, 計46）
```
愛, 欲, 悪, 遊, H, 秘, 食, 友, 悩, 休, 嘘, 家, 妄, 想, 気, 無, 恐, 敬, 好, 逃,
怒, 抱, 寂, 楽, 嫌, 苦, 虜, 疑, 告, 疲, 忘, 敵, 餌, 学, 泣, 羨, 癒, 幸, 妬, 変,
貧, 謎, 仏, 犬, 猫, 国
```
- `H` は **ASCII 半角の `H`** で固定する（全角 `Ｈ` は前処理で半角へ正規化）。
- `label_id` は上記の出現順で `0`〜`45` を割り当てる（愛=0, 欲=1, … 国=45）。
- これを `v0` 在庫として固定し、`label_map.json`（id↔文字）として凍結する。表記揺れ（全角/半角・異体字）の正規化ルールを併せて定義する。

### QA 専用ラベル `分類不能`（重要）
- 観測 46 に **`分類不能` を 1 つだけ追加**し、パイロット在庫は **計47ラベル**とする。`label_id=46` を割り当てる。
- `分類不能` は **ラベリング QA 専用**。Gemini パイロットラベリングでは「46 のどれにも当てはまらない／判断不能」の逃がし先として**使ってよい**。
- **本番／ブラウザ推論は `分類不能` を出力してはならない**。最終モデルは必ず観測 46 のいずれか 1 つを出力する。`分類不能` が付いたサンプルは学習前に「最近接ラベルへ再割当」または「学習データから除外」し、46 クラスのヘッドには含めない。
- `分類不能` 率（例: >3%）が高い文字傾向は、在庫の過不足や本家観測漏れの検出材料とし、`v1` 再凍結の判断に使う。

### 旧暫定セットとの差分（追加・削除を明示）
パイロット在庫は、直前の**暫定 42 ラベル**
（愛, 欲, 悪, 遊, H, 秘, 食, 友, 悩, 休, 嘘, 家, 妄, 想, 気, 無, 恐, 敬, 私, 学, 楽, 怒, 哀, 癒, 疲, 眠, 金, 汗, 猫, 犬, 酒, 変, 幸, 妬, 泣, 忘, 逃, 恋, 真, 希, 鬱, 推）
を観測 46 に合わせて再構成したものである。内訳は **42 中 31 を維持・11 を削除・15 を新規追加**（31 + 15 = 46）。

- **新規追加（観測 46 にあり暫定 42 になかった 15 文字）**:
  `好, 抱, 寂, 嫌, 苦, 虜, 疑, 告, 敵, 餌, 羨, 貧, 謎, 仏, 国`
  暫定セットでは漏れていたが本家で観測されたため追加。
- **削除（暫定 42 にあったが観測 46 になく、パイロット在庫から外す 11 文字）**:
  `私, 哀, 眠, 金, 汗, 酒, 恋, 真, 希, 鬱, 推`
  本家観測リストに存在しないため除外。特に推測由来だった `私, 真, 希, 鬱, 推` に加え、`哀・眠・金・汗・酒・恋` も観測 46 に含まれず除外となる。
  - 補足: 直前の 15 ラベル案で導入していた `夢, 体` と、上記 `金` は、いずれも観測 46 に無いためパイロット在庫には**含めない**。
- 在庫を増やす場合は、本家での再観測を条件とし、Phase 0 の凍結手順を経て `v1` として再凍結する。

## 3. Nostr データ収集設計（日本語投稿 約2000件・多様性最大化）

### 目的量と方針
- 最終ラベリング対象は**約2000件**の日本語投稿。クラス不均衡と除外を見込み、**生取得は 6000〜8000 件**を狙い、フィルタ・dedupe・サンプリングで 2000 件に絞る。
- 単一の人気リレー・単一時間帯に偏らせず、**日本語ユーザの多様性（著者・話題・時間帯・コミュニティ）を最大化**する。

### リレーミックス
- 大規模アグリゲータ + 日本語圏リレーを混在させ、同一投稿を複数経路から拾えるようにする。
  - 例: `wss://relay.nostr.band`, `wss://yabu.me`, `wss://r.kojira.io`, `wss://relay-jp.nostr.wirednet.jp`, `wss://nos.lol`, `wss://relay.damus.io`。
- 取得は kind:1（テキストノート）中心。各リレーから独立に収集し、後段の dedupe で統合する。

### タイムスライス（期間分散）
- 直近 30〜45 日を**複数ウィンドウに分割**（例: 1〜3 日ごとのスライス）し、各ウィンドウから上限付きで取得。
- 現行の `until` ページングを流用し、各ウィンドウ内でも `until` を繰り上げてページングして取りこぼしを防ぐ。
- 朝・昼・夜の時間帯がスライス間で平準化されるよう、ウィンドウ境界を均等に配置する。

### 著者あたり上限（per-author cap）
- **本収集（2000件規模）**: 1 pubkey あたり最大 **10 件**。特定ユーザの口調への過学習を防ぐ。
- **パイロット小規模収集**: 多様性を最優先し、1 pubkey あたり **1 件**（`per_author_cap=1`）。

### 重複排除（de-duplication）
- `event.id` で完全重複除去（複数リレー経由の同一イベントを統合）。
- `content` 正規化後（空白圧縮・URL除去・小文字化・記号除去）の**ハッシュで準重複除去**（コピペ・定型文・bot 連投を吸収）。
- リレーをまたいで残った重複は 1 件に畳み、`relay` を配列に集約する。

### 日本語判定ヒューリスティック
- **かな比率**: ひらがな/カタカナが総文字数の **≥12%**（短文でも拾える緩め）。
- **CJK 比率**: CJK が **≥35%**（漢字主体の投稿を救済）。上記いずれかを満たせば日本語候補。
- **長さ下限**: 正規化後 **5 文字以上**（実質 1 単語・1 絵文字を除外）。
- Latin-only・絵文字-only・URL-only をスコアで除外。中国語/韓国語の取りこぼしは、かな比率が 0 かつ特定字種に偏るケースを弾いて緩和。

### スパム・低品質除外
- 同一文面の大量投稿、過剰な URL/ハッシュタグ、招待・宣伝・アフィリエイト定型文。
- リポスト/引用のみ（kind:6、`content` 空で `e` タグ参照のみ等）。
- bot 連投（同一 pubkey の高頻度同型投稿）。
- NSFW/ポリシー違反・暴力扇動・武器販売等はフラグ付けし、収集段階で除外または保留。

### 人手レビュー キュー
- 自動フィルタを通過したもののうち、**言語スコアが境界値付近**・**準重複の代表**・**スパム疑い**を `review` キューへ回す。
- パイロットでは**全件**を、本収集では**層化サンプル**を人手確認し、確定分だけをラベリング対象（`approved`）へ昇格させる。

### パイロット先行の進め方（20 → 200 → 2000）
1. **20 件**: 収集パイプラインとラベリングをエンドツーエンドで疎通確認（§12）。人手で全件レビューし、フィルタ閾値・在庫（46+`分類不能`）の妥当性を点検。
2. **200 件**: リレーミックス・タイムスライスを本番設定で回し、`分類不能` 率・準重複率・言語誤検出率を実測して閾値を調整。
3. **2000 件**: 確定した設定で本収集。クラス分布を見ながら少数クラスを追い集めし、最終ラベリングへ。

### 保存スキーマ（収集生データ）
各投稿につき以下を保存：
- `event_id` (`id`)
- `pubkey`
- `created_at`
- `content`
- `relay`（取得元リレーURL。複数経路なら配列）
- `review_status`（`approved` / `review` / `excluded`）

## 4. 教師ラベル生成（Gemini API / `gemini-3.1-flash-lite`）

### 概要
- 学習用の教師ラベルを **Gemini API（モデル: `gemini-3.1-flash-lite`）** で生成する。
- 1投稿 → 観測 46 ラベルのうち**単一ラベル**を割り当てる。判断不能時のみ QA 専用の `分類不能` を許容する。

### プロンプト戦略
- システム指示で「あなたは脳内メーカー風に、投稿者の頭の中を表す**1文字**を選ぶ分類器」と定義。
- **46文字の在庫リストと各文字の意味ガイドライン**をプロンプトに埋め込む（`label_map` と短い定義）。
- 出力は**列挙された 46 ラベル**から選ぶよう厳格に制約（自由文字の新規生成を禁止）。**どれにも該当しない場合のみ `分類不能` を許可**する。
- 投稿本文は前処理（過剰な空白・URLは要約/除去）して渡す。

### 出力 JSON スキーマ（単一ラベル制約）
```json
{
  "label": "愛",
  "label_id": 0,
  "confidence": 0.0,
  "rationale": "短い根拠（日本語、1〜2文）",
  "is_uncertain": false
}
```
- `label` は観測 46 在庫のいずれか（または QA 期間のみ `分類不能`）。
- `confidence` は 0.0–1.0。
- `rationale` はQA・誤り分析用の根拠。
- スキーマ検証に失敗した出力は無効として再試行。

### 2パスプロンプト（低確信度の精緻化）
- **1パス目**: 上記スキーマで全件を分類。
- **低確信度（例: `confidence < 0.6` または `is_uncertain=true`）の項目のみ2パス目**を実施：
  - 候補上位2〜3ラベルを提示させ、各候補の根拠を比較させた上で最終1ラベルを再選択。
  - 必要なら few-shot 例（境界事例）を追加して曖昧さを減らす。
- 2パス後もしきい値未満の項目は**人手スポットチェック**へ回す。

### リトライ・フォールバック
- API エラー／スキーマ不一致／レート制限は指数バックオフで再試行（§5）。
- 規定回数失敗した投稿は `pending` として隔離し、ラベルは付けない（学習データから除外可能にする）。

### 人手スポットチェック
- 全体から**層化サンプリング**（各ラベルから一定数）でレビュー。
- 低確信度群・`分類不能`群は重点的にレビュー。
- レビュー結果は混同しやすいラベル対の検出・プロンプト改善・在庫見直しにフィードバック。

## 5. 並列化とレート制限セーフ戦略

### 前提（要確認・調整）
- **RPM（requests/min）**・**TPM（tokens/min）**の上限はアカウントのクォータに依存するため、**保守的な初期値**を設定し、実測で調整する（例: RPM=安全側の上限の70%を上限とする）。
- 1リクエストあたりの入出力トークン量を見積もり、TPM を超えないバッチサイズを算出。

### バッチ・ワーカー設計
- **バッチング**: 1リクエストに複数投稿を入れず、**1投稿=1リクエスト**を基本とする（単一ラベル制約とスキーマ検証を簡潔に保つため）。スループットはワーカー並列で確保。
- **ワーカー数**: `min(RPM上限 / 1分あたり想定リクエスト, 同時実行上限)` から決定（例: 4〜8 並列から開始）。
- レートリミッタ（トークンバケツ）を共有し、RPM/TPM の両方を尊重。

### バックオフ
- 429/5xx は**指数バックオフ + ジッター**（例: base=1s, factor=2, max=60s, full jitter）。
- `Retry-After` ヘッダがあれば優先。

### チェックポイント
- 進捗を **`event_id` 単位で永続化**（`done` / `pending` / `failed`）。
- 中断・再開に強い設計（処理済みはスキップ）。
- 定期フラッシュで途中結果を JSONL に追記保存。

## 6. モデル設計（`ruri-v3-30m` + 分類ヘッド）

### ベース
- 日本語埋め込みモデル **`ruri-v3-30m`** をエンコーダとして使用し、上に**分類ヘッド**を載せる。

### 構成
- **プーリング**: mean pooling（attention mask 加重平均）を基本。`[CLS]`/last-token も比較対象として検証。
- **隠れ層**: `hidden = Linear(emb_dim → 256) + GELU`。
- **ドロップアウト**: 0.1〜0.3（過学習を見て調整）。
- **出力**: `Linear(256 → 46)` + softmax（`分類不能` は含めない）。
- **損失**: クロスエントロピー。
- **クラス重み付け**: クラス頻度の逆数ベースで重み付け（不均衡対策）。
- **focal loss（任意）**: 不均衡が強い場合に `gamma=2` 程度で代替検討。

### 学習設定
- ベースエンコーダは初期は凍結 → ヘッド学習 → 後段で低LRで部分fine-tune（2段階）も検討。
- オプティマイザ AdamW、線形ウォームアップ + 減衰。早期終了（val macro-F1 監視）。

### データ分割
- **train / val / test = 80 / 10 / 10**。
- **pubkey でグループ分割**（同一著者が複数splitに跨らない）。リーク防止。
- ラベル層化を可能な範囲で維持。

### データ拡張（アイデア）
- 軽微なノイズ注入（絵文字・記号の付与/除去、空白正規化のばらつき）。
- 同義言い換え（控えめに。意味=ラベルが変わらない範囲）。
- 少数クラスのオーバーサンプリング（重複 or 拡張）。
- 拡張は**train のみ**に適用し、val/test は素のまま。

## 7. データセット形式（JSONL 例）

### 生データ（raw）
```json
{"event_id":"abc123","pubkey":"npub_xxx","created_at":1733980800,"content":"今日はずっと配信見て遊んでた…最高","relay":["wss://relay.example"]}
```

### ラベル付与済み（labeled）
```json
{"event_id":"abc123","content":"今日はずっと配信見て遊んでた…最高","label":"遊","label_id":3,"confidence":0.82,"rationale":"娯楽・遊びへの没頭","pass":1,"source":"gemini-3.1-flash-lite","reviewed":false}
```

### 学習用（train-ready）
```json
{"text":"今日はずっと配信見て遊んでた…最高","label_id":3,"split":"train"}
```
- `train-ready` は最小フィールド（`text`, `label_id`, `split`）に正規化。`分類不能` は除外済み・正規化済み（`label_id` は 0–45 のみ）。

## 8. ラベルQA・評価

### ラベルQA
- 層化サンプルの人手レビュー（§4）。
- **混同しやすいラベル対**（例: 愛/欲, 食/欲・餌, 悩/逃, 寂/泣, 嫌/悪）を定義し、ガイドラインを明確化。
- `分類不能` 率・低確信度率をモニタし、在庫凍結 `v0`（46 ラベル）の妥当性を検証。

### 評価指標
- **macro-F1**（クラス不均衡下の主指標）。
- **top-1 accuracy**。
- 参考: per-class precision/recall、top-3 accuracy。
- **目標例**: macro-F1 ≥ 0.5、top-1 accuracy ≥ 0.6（初期ベースライン目標。データ品質で見直す）。

### 混同行列レビュー
- test の混同行列を可視化し、系統的誤り（特定ペアの取り違え）を特定 → ガイドライン/在庫/拡張へフィードバック。

### キャリブレーション
- 信頼度の温度スケーリング（temperature scaling）で確率を補正。
- reliability diagram / ECE で評価。

### 棄却しきい値（オフラインQAのみ）
- **abstain しきい値はオフラインQA分析の目的に限定**して使用（低確信度サンプルの抽出・人手レビュー対象選定）。
- **最終ブラウザモデルは棄却しない**。実行時は常に argmax で観測 46 ラベルのいずれか1つを出力する（`分類不能` は出さない）。

## 9. ブラウザ推論デプロイ計画

### エクスポート
- 学習済みモデル（エンコーダ + 分類ヘッド）を **ONNX にエクスポート**。
- トークナイザ設定・`label_map.json`（id↔文字）を同梱。

### 量子化
- **動的量子化（int8）**でサイズ・レイテンシ削減。
- 量子化前後で macro-F1 の劣化を比較し、許容範囲を確認。

### ランタイム
- **transformers.js** もしくは **onnxruntime-web** を採用。
  - transformers.js: トークナイズ＋推論を一体で扱いやすい。
  - onnxruntime-web: 軽量・実行制御しやすい（WASM/WebGPU バックエンド選択）。
- WebGPU が使える環境では高速化、無い場合は WASM フォールバック。

### 後処理
- ロジット → softmax → **argmax で1ラベル**を選択。
- `label_map.json` を引いて**1文字に変換**して表示。
- 入力前処理（空白・URL正規化）はブラウザ側でも学習時と同一ルールを適用。

### フォールバック UX
- モデルロード失敗・WASM 非対応時は、現行のヒューリスティック実装に**グレースフルにフォールバック**。
- ロード中はプレースホルダ表示。初回ロードはキャッシュ（Service Worker / IndexedDB）。

### サイズ・レイテンシの懸念
- `ruri-v3-30m` ＋ int8 でもモデル数十MB規模になり得る → 初回DLサイズを明示し、キャッシュ前提。
- 1推論のレイテンシ目標を設定（例: WASM で数百ms以内）。長文は最大トークン長で truncation。

## 10. 推奨実装順序（フェーズ）

- **Phase 0 — 在庫凍結**: 観測 46 ラベル `v0` を確定（+ QA 専用 `分類不能`）、`label_map.json` 作成、正規化ルール定義。
- **Phase 1 — データ収集**: Nostr から日本語投稿を収集・フィルタ・dedupe、生データ JSONL 保存。パイロット 20 → 200 → 2000 の順で進める（§3, §12）。
- **Phase 2 — 教師ラベル**: Gemini で1パス分類 → 低確信度を2パス精緻化 → 人手スポットチェック。
- **Phase 3 — データ整形**: `分類不能` の再割当/除外、train-ready JSONL、pubkey グループ分割。
- **Phase 4 — 学習**: `ruri-v3-30m` + ヘッド学習、クラス重み/（任意）focal loss、early stopping。
- **Phase 5 — 評価**: macro-F1 / top-1、混同行列、キャリブレーション、誤り分析 → 必要なら Phase 0〜2 へ反復。
- **Phase 6 — エクスポート/量子化**: ONNX 化・int8 量子化・劣化検証。
- **Phase 7 — ブラウザ統合**: transformers.js/onnxruntime-web 組込、フォールバックUX、キャッシュ、計測。

## 11. リスクと未解決事項

- **在庫の妥当性**: 公式の機械可読な正規一覧が無いため、観測 46 ラベル `v0` でも実データ分布をうまく覆えない可能性。`分類不能` 率で監視し反復。
- **教師ラベルの質**: Gemini 出力にバイアス・誤りが混入。人手レビュー比率と2パスで緩和するが、上限性能を規定する。
- **クラス不均衡**: 愛・遊 などに偏りやすい。重み付け/拡張/サンプリングでも少数クラス（嘘・逃 など）の F1 が伸びにくい懸念。
- **言語フィルタの取りこぼし**: ヒューリスティックで日本語以外や定型スパムが混入する可能性。
- **データ分布のドリフト**: Nostr の話題は時期で変動。収集期間と本番のズレ。
- **プライバシ・倫理**: 個人の投稿を「頭の中1文字」にラベル化することへの配慮。表示は娯楽目的である旨を明示。
- **モデルサイズ vs 体験**: 30m 量子化でも初回DLが重い場合のUX。さらに小型化（蒸留）の要否。
- **未解決（要決定）**:
  - Gemini クォータ（RPM/TPM）の実値とコスト試算。
  - 在庫を `v0`(観測46) で固定するか、本家再観測を条件に評価後の再凍結 `v1` で増減するか。
  - 量子化後の許容劣化幅（macro-F1 の許容低下）。
  - ブラウザ最大トークン長と truncation 方針。

## 12. パイロット実行（20 → 200 → 2000 の起点）

パイロットは小規模からエンドツーエンドで疎通させ、在庫（46 + QA 専用 `分類不能`）・収集フィルタ・Gemini ラベリングを実データで検証する。

### 成果物（最初の 20 件パイロット）
- **`data/pilot/nostr-jp-sample-20.json`** — 最初の 20 サンプル収集結果。リレーミックス・タイムスライス・`per_author_cap=1`・dedupe・日本語判定・除外ポリシーを適用した収集物。各件に `event_id` / `pubkey` / `created_at` / `content` / `relay` / `review_status` を保持。
- **`data/pilot/gemini-labels-20.json`** — 上記 20 件に対する Gemini（`gemini-3.1-flash-lite`）のラベリング出力。各件 §4 のスキーマ（`label` / `label_id` / `confidence` / `rationale` / `is_uncertain`）で、`label` は観測 46 または `分類不能`。

### API ロギング（必須）
- Gemini への**生の入力（プロンプト・投稿本文）と生の出力（JSON 応答）を全件ログ**に残す（`event_id` で突合可能に）。
- **失敗（API エラー・レート制限・スキーマ不一致・再試行・最終 `pending`）も記録**し、再現・原因分析・プロンプト改善に使う。
- ログは追記式（JSONL 等）で、20 → 200 → 2000 を通して同一フォーマットで蓄積する。

### 進め方
1. **20 件**: `nostr-jp-sample-20.json` を収集 → `gemini-labels-20.json` を生成 → 全件人手レビュー。`分類不能` の出方・誤分類・混同ペアを確認し、プロンプトと在庫を点検。
2. **200 件**: 収集設定を本番化し、`分類不能` 率・準重複率・言語誤検出率を実測して閾値とプロンプトを調整。
3. **2000 件**: 確定設定で本収集・本ラベリングへ移行（§3 / §4 / §10 Phase 1–2）。
