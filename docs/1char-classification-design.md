# 1文字分類（脳内メーカー風）設計メモ

> 本ドキュメントは**設計のみ**。コードは含まない。Nostr の1投稿を入力とし、オリジナルの脳内メーカーのように「1文字」を出力する分類器を、データ収集→教師ラベル付与→学習→ブラウザ推論まで一気通貫で設計する。

---

## 1. ゴールと非ゴール

### ゴール
- **入力**: Nostr の1投稿（`content` テキスト1件）。
- **出力**: 脳内メーカー風の漢字／記号 **1文字**（例: 愛, 欲, H ...）。
- **15ラベル**の固定クラス集合への単一ラベル分類とする。
- 最終的に**ブラウザ完結（静的・オフライン）**で推論できること。現行アプリが採用しているヒューリスティックなトークナイズを、学習済み小型モデルに置き換える。
- 最終ブラウザモデルは**常に15ラベルのいずれか1つを必ず出力する**（棄却・UNKを返さない）。

### 非ゴール
- 複数文字・文章生成（例: 「愛と欲」など複合表示）は対象外（将来拡張）。
- 脳内メーカー本家の内部ロジック再現や著作物の複製は目的としない。あくまで「1文字に要約する」体験の独自実装。
- サーバ常時推論・課金APIへの実行時依存は非ゴール（学習時のみ外部APIを使う）。
- ユーザ識別・プロファイリング目的の利用は非ゴール。

---

## 2. ラベル集合計画

### 方針
- 脳内メーカー風の**1文字キャラクター在庫**を採用する。
- 在庫は**オリジナル（脳内メーカー本家）で公開・観測された実在ラベル**を基準に確定する。以前の暫定 v0（約42ラベル）は推測由来の文字を多く含んでいたため破棄し、**本家チェックで裏付けの取れた15文字**へ縮小する。
- 凍結後はバージョン管理し、勝手に増減させない。

### 固定ラベル在庫（Fixed Set, 計15）
```
愛, 欲, 悪, 遊, H, 秘, 食, 友, 悩, 休, 金, 嘘, 夢, 逃, 体
```
- `label_id` は上記の出現順で `0`〜`14` を割り当てる（例: 愛=0, 欲=1, … 体=14）。
- これを `v0` 在庫として固定し、`label_map.json`（id↔文字）として凍結する。
- 表記の揺れ（全角/半角の `H` など）は正規化ルールを定義しておく。

### 暫定ラベルの削除（重要）
- 旧 v0 working set に含めていた **私, 真, 希, 鬱, 推** などの暫定ラベルは、**オリジナルサイトのチェックで裏付けが取れなかった**ため在庫から除外した。
- 同様に、推測で並べていたその他の文字（家・妄・想・気・無・恐・敬・学・楽・怒・哀・癒・疲・眠・汗・猫・犬・酒・変・幸・妬・泣・忘・恋 など）も裏付け不足のため除外している。
- 在庫を増やす場合は、本家での裏付け（公開・観測）を条件とし、Phase 0 の凍結手順を経て `v1` として再凍結する。

### UNK / その他バケツの扱い
- **UNK/other バケツは「ラベリングQAの期間中のみ」保持する**。
  - 教師ラベル付与時に「どれにも当てはまらない／判断不能」を逃がす先として使い、在庫の過不足を検出する。
  - UNK が一定割合（例: >3%）に達した文字傾向を分析し、在庫の追加・統合を検討する材料にする。
- **最終ブラウザモデルには UNK を含めない**。最終モデルは必ず15ラベルのいずれかを出力する。UNK 相当のサンプルは学習前に「最近接ラベルへ再割当」または「学習データから除外」する。

## 3. Nostr データ収集設計（日本語投稿 約2000件）

### 目的量
- ラベリング対象として**約2000件**の日本語投稿を確保。クラス不均衡を考慮し、収集段階では多めに集めてからサンプリングする（例: 5000〜8000件収集 → 2000件に絞る）。

### 多様性ソース
- 複数リレーから収集（現行の既定リレー群 + 主要な日本語圏リレー）。
- 取得対象は kind:1（テキストノート）中心。
- 話題の偏りを避けるため、時間帯・期間を分散（例: 直近30日を複数ウィンドウに分割してページング取得）。現行の `until` ページングを流用。

### フィルタ・品質ルール
- **著者あたり上限（per-author cap）**: 1 pubkey あたり最大 N 件（例: 10件）。特定ユーザの口調へ過学習しないため。
- **重複排除（dedupe）**:
  - `event.id` で完全重複除去。
  - `content` 正規化後（空白・URL除去・小文字化）のハッシュで準重複除去。
- **言語フィルタ（ヒューリスティック）**:
  - ひらがな／カタカナの出現比率がしきい値以上（例: かな文字が総文字数の20%以上）。
  - CJK 比率と Latin-only 比率でスコアリングし、英語専用・絵文字専用を除外。
- **除外対象**:
  - スパム（同一文面の大量投稿、過剰なURL/ハッシュタグ、招待・宣伝定型文）。
  - リポスト/引用のみ（kind:6、`content` が空で `e` タグ参照のみ等）。
  - **極端に短い投稿**（例: 正規化後10文字未満、または実質1単語）。
  - NSFW/ポリシー違反は収集段階でフラグ付けし、扱いを別途判断。

### 保存スキーマ（収集生データ）
各投稿につき以下を保存：
- `event_id` (`id`)
- `pubkey`
- `created_at`
- `content`
- `relay`（取得元リレーURL。複数なら配列）

## 4. 教師ラベル生成（Gemini API / `gemini-3.1-flash-lite`）

### 概要
- 学習用の教師ラベルを **Gemini API（モデル: `gemini-3.1-flash-lite`）** で生成する。
- 1投稿 → 15ラベルのうち**単一ラベル**を割り当てる。

### プロンプト戦略
- システム指示で「あなたは脳内メーカー風に、投稿者の頭の中を表す**1文字**を選ぶ分類器」と定義。
- **15文字の在庫リストと各文字の意味ガイドライン**をプロンプトに埋め込む（`label_map` と短い定義）。
- 出力は**列挙されたラベルのみ**から選ぶよう厳格に制約（自由文字の新規生成を禁止）。
- 投稿本文は前処理（過剰な空白・URLは要約/除去）して渡す。

### 出力 JSON スキーマ（単一ラベル制約）
```json
{
  "label": "愛",
  "label_id": 0,
  "confidence": 0.0,
  "rationale": "短い根拠（日本語、1〜2文）",
  "is_uncertain": false
}
```
- `label` は15在庫のいずれか（または QA 期間のみ `UNK`）。
- `confidence` は 0.0–1.0。
- `rationale` はQA・誤り分析用の根拠。
- スキーマ検証に失敗した出力は無効として再試行。

### 2パスプロンプト（低確信度の精緻化）
- **1パス目**: 上記スキーマで全件を分類。
- **低確信度（例: `confidence < 0.6` または `is_uncertain=true`）の項目のみ2パス目**を実施：
  - 候補上位2〜3ラベルを提示させ、各候補の根拠を比較させた上で最終1ラベルを再選択。
  - 必要なら few-shot 例（境界事例）を追加して曖昧さを減らす。
- 2パス後もしきい値未満の項目は**人手スポットチェック**へ回す。

### リトライ・フォールバック
- API エラー／スキーマ不一致／レート制限は指数バックオフで再試行（§5）。
- 規定回数失敗した投稿は `pending` として隔離し、ラベルは付けない（学習データから除外可能にする）。

### 人手スポットチェック
- 全体から**層化サンプリング**（各ラベルから一定数）でレビュー。
- 低確信度群・UNK群は重点的にレビュー。
- レビュー結果は混同しやすいラベル対の検出・プロンプト改善・在庫見直しにフィードバック。

## 5. 並列化とレート制限セーフ戦略

### 前提（要確認・調整）
- **RPM（requests/min）**・**TPM（tokens/min）**の上限はアカウントのクォータに依存するため、**保守的な初期値**を設定し、実測で調整する（例: RPM=安全側の上限の70%を上限とする）。
- 1リクエストあたりの入出力トークン量を見積もり、TPM を超えないバッチサイズを算出。

### バッチ・ワーカー設計
- **バッチング**: 1リクエストに複数投稿を入れず、**1投稿=1リクエスト**を基本とする（単一ラベル制約とスキーマ検証を簡潔に保つため）。スループットはワーカー並列で確保。
- **ワーカー数**: `min(RPM上限 / 1分あたり想定リクエスト, 同時実行上限)` から決定（例: 4〜8 並列から開始）。
- レートリミッタ（トークンバケツ）を共有し、RPM/TPM の両方を尊重。

### バックオフ
- 429/5xx は**指数バックオフ + ジッター**（例: base=1s, factor=2, max=60s, full jitter）。
- `Retry-After` ヘッダがあれば優先。

### チェックポイント
- 進捗を **`event_id` 単位で永続化**（`done` / `pending` / `failed`）。
- 中断・再開に強い設計（処理済みはスキップ）。
- 定期フラッシュで途中結果を JSONL に追記保存。

## 6. モデル設計（`ruri-v3-30m` + 分類ヘッド）

### ベース
- 日本語埋め込みモデル **`ruri-v3-30m`** をエンコーダとして使用し、上に**分類ヘッド**を載せる。

### 構成
- **プーリング**: mean pooling（attention mask 加重平均）を基本。`[CLS]`/last-token も比較対象として検証。
- **隠れ層**: `hidden = Linear(emb_dim → 256) + GELU`。
- **ドロップアウト**: 0.1〜0.3（過学習を見て調整）。
- **出力**: `Linear(256 → 15)` + softmax。
- **損失**: クロスエントロピー。
- **クラス重み付け**: クラス頻度の逆数ベースで重み付け（不均衡対策）。
- **focal loss（任意）**: 不均衡が強い場合に `gamma=2` 程度で代替検討。

### 学習設定
- ベースエンコーダは初期は凍結 → ヘッド学習 → 後段で低LRで部分fine-tune（2段階）も検討。
- オプティマイザ AdamW、線形ウォームアップ + 減衰。早期終了（val macro-F1 監視）。

### データ分割
- **train / val / test = 80 / 10 / 10**。
- **pubkey でグループ分割**（同一著者が複数splitに跨らない）。リーク防止。
- ラベル層化を可能な範囲で維持。

### データ拡張（アイデア）
- 軽微なノイズ注入（絵文字・記号の付与/除去、空白正規化のばらつき）。
- 同義言い換え（控えめに。意味=ラベルが変わらない範囲）。
- 少数クラスのオーバーサンプリング（重複 or 拡張）。
- 拡張は**train のみ**に適用し、val/test は素のまま。

## 7. データセット形式（JSONL 例）

### 生データ（raw）
```json
{"event_id":"abc123","pubkey":"npub_xxx","created_at":1733980800,"content":"今日はずっと配信見て遊んでた…最高","relay":["wss://relay.example"]}
```

### ラベル付与済み（labeled）
```json
{"event_id":"abc123","content":"今日はずっと配信見て遊んでた…最高","label":"遊","label_id":3,"confidence":0.82,"rationale":"娯楽・遊びへの没頭","pass":1,"source":"gemini-3.1-flash-lite","reviewed":false}
```

### 学習用（train-ready）
```json
{"text":"今日はずっと配信見て遊んでた…最高","label_id":3,"split":"train"}
```
- `train-ready` は最小フィールド（`text`, `label_id`, `split`）に正規化。UNK は除外済み・正規化済み。

## 8. ラベルQA・評価

### ラベルQA
- 層化サンプルの人手レビュー（§4）。
- **混同しやすいラベル対**（例: 愛/欲, 食/欲, 悩/逃）を定義し、ガイドラインを明確化。
- UNK 率・低確信度率をモニタし、在庫凍結 `v0` の妥当性を検証。

### 評価指標
- **macro-F1**（クラス不均衡下の主指標）。
- **top-1 accuracy**。
- 参考: per-class precision/recall、top-3 accuracy。
- **目標例**: macro-F1 ≥ 0.5、top-1 accuracy ≥ 0.6（初期ベースライン目標。データ品質で見直す）。

### 混同行列レビュー
- test の混同行列を可視化し、系統的誤り（特定ペアの取り違え）を特定 → ガイドライン/在庫/拡張へフィードバック。

### キャリブレーション
- 信頼度の温度スケーリング（temperature scaling）で確率を補正。
- reliability diagram / ECE で評価。

### 棄却しきい値（オフラインQAのみ）
- **abstain しきい値はオフラインQA分析の目的に限定**して使用（低確信度サンプルの抽出・人手レビュー対象選定）。
- **最終ブラウザモデルは棄却しない**。実行時は常に argmax で15ラベルのいずれか1つを出力する。

## 9. ブラウザ推論デプロイ計画

### エクスポート
- 学習済みモデル（エンコーダ + 分類ヘッド）を **ONNX にエクスポート**。
- トークナイザ設定・`label_map.json`（id↔文字）を同梱。

### 量子化
- **動的量子化（int8）**でサイズ・レイテンシ削減。
- 量子化前後で macro-F1 の劣化を比較し、許容範囲を確認。

### ランタイム
- **transformers.js** もしくは **onnxruntime-web** を採用。
  - transformers.js: トークナイズ＋推論を一体で扱いやすい。
  - onnxruntime-web: 軽量・実行制御しやすい（WASM/WebGPU バックエンド選択）。
- WebGPU が使える環境では高速化、無い場合は WASM フォールバック。

### 後処理
- ロジット → softmax → **argmax で1ラベル**を選択。
- `label_map.json` を引いて**1文字に変換**して表示。
- 入力前処理（空白・URL正規化）はブラウザ側でも学習時と同一ルールを適用。

### フォールバック UX
- モデルロード失敗・WASM 非対応時は、現行のヒューリスティック実装に**グレースフルにフォールバック**。
- ロード中はプレースホルダ表示。初回ロードはキャッシュ（Service Worker / IndexedDB）。

### サイズ・レイテンシの懸念
- `ruri-v3-30m` ＋ int8 でもモデル数十MB規模になり得る → 初回DLサイズを明示し、キャッシュ前提。
- 1推論のレイテンシ目標を設定（例: WASM で数百ms以内）。長文は最大トークン長で truncation。

## 10. 推奨実装順序（フェーズ）

- **Phase 0 — 在庫凍結**: 本家で裏付けの取れた15ラベル `v0` を確定、`label_map.json` 作成、正規化ルール定義。
- **Phase 1 — データ収集**: Nostr から日本語投稿を収集・フィルタ・dedupe、生データ JSONL 保存（約2000件確保）。
- **Phase 2 — 教師ラベル**: Gemini で1パス分類 → 低確信度を2パス精緻化 → 人手スポットチェック。
- **Phase 3 — データ整形**: UNK 処理、train-ready JSONL、pubkey グループ分割。
- **Phase 4 — 学習**: `ruri-v3-30m` + ヘッド学習、クラス重み/（任意）focal loss、early stopping。
- **Phase 5 — 評価**: macro-F1 / top-1、混同行列、キャリブレーション、誤り分析 → 必要なら Phase 0〜2 へ反復。
- **Phase 6 — エクスポート/量子化**: ONNX 化・int8 量子化・劣化検証。
- **Phase 7 — ブラウザ統合**: transformers.js/onnxruntime-web 組込、フォールバックUX、キャッシュ、計測。

## 11. リスクと未解決事項

- **在庫の妥当性**: 公式の機械可読な正規一覧が無いため、本家裏付けの15ラベル `v0` でも実データ分布をうまく覆えない可能性。UNK 率で監視し反復。
- **教師ラベルの質**: Gemini 出力にバイアス・誤りが混入。人手レビュー比率と2パスで緩和するが、上限性能を規定する。
- **クラス不均衡**: 愛・遊 などに偏りやすい。重み付け/拡張/サンプリングでも少数クラス（嘘・逃 など）の F1 が伸びにくい懸念。
- **言語フィルタの取りこぼし**: ヒューリスティックで日本語以外や定型スパムが混入する可能性。
- **データ分布のドリフト**: Nostr の話題は時期で変動。収集期間と本番のズレ。
- **プライバシ・倫理**: 個人の投稿を「頭の中1文字」にラベル化することへの配慮。表示は娯楽目的である旨を明示。
- **モデルサイズ vs 体験**: 30m 量子化でも初回DLが重い場合のUX。さらに小型化（蒸留）の要否。
- **未解決（要決定）**:
  - Gemini クォータ（RPM/TPM）の実値とコスト試算。
  - 在庫を `v0`(15) で固定するか、本家裏付けを条件に評価後の再凍結 `v1` で増やすか。
  - 量子化後の許容劣化幅（macro-F1 の許容低下）。
  - ブラウザ最大トークン長と truncation 方針。
